Overview — one vault, one workflow

Every merchant's cards follow the same path. Source files arrive in different shapes, but import and validation normalize each one into a single canonical card record inside the Secure Card Vault. From there, per-order output rules decide how each fulfillment request is packaged for the customer.

MODE A Repackage — the vault exports the stored credentials (URLs, codes, PINs) as a password-protected Excel file.
MODE B Generate — the vault renders a PDF card per credential and bundles them in a password-protected ZIP.

Because every merchant flows through this same spine, adding a new merchant that fits an existing credential pattern is a configuration and end-to-end validation task — not new software.

The customer-ready file is an internal fulfillment file: Progressive downloads it from the vault and delivers it to the customer through your existing process. Exact export layouts are validated against Progressive's known-good example files and confirmed together at kickoff.

URL + Challenge Code — CashStar merchants

Tim Hortons · Best Buy · Sephora · DoorDash · Earls · The Keg · other CashStar-delivered brands

All CashStar-delivered brands arrive the same way: a links file with one row per card, carrying a redemption URL and a challenge code. One import mapping covers the whole family.

Credential shape: Redemption URL + challenge code Output: Mode A — Repackage

Why this matters: every additional CashStar brand reuses this exact pipeline — new brands are onboarded by configuring the mapping and validating one file end-to-end.

URL + Account # + PIN — PC / Loblaws allocation

Loblaws · Shoppers Drug Mart · sibling banners under the same parent

The PC / Loblaws family carries three credential fields per card: a redemption URL, an account number, and a PIN. Because every sibling banner under the parent uses the same file format, one import mapping covers all of them.

Credential shape: Redemption URL + account # + PIN Output: Mode A — Repackage

One mapping, many banners: sibling banners under one parent share one file format, so onboarding another banner in this family is a configuration check, not a new integration.

Card # + PIN — Code-and-PIN merchants

Cara brands · Chapters-Indigo

These merchants supply a card number and PIN per card — no redemption URL. The vault stores both fields on the canonical card record and repackages them at fulfillment.

Credential shape: Card number + PIN Output: Mode A — Repackage (default) Per-order option: Mode B — Generated PDF cards

Output format is an order-level rule, not fixed per merchant. Chapters-Indigo orders, for example, can also be output as generated PDF cards (Mode B) when the order calls for it — the same vault records feed either output.

Claim Code → Generated PDF — Amazon

Amazon

Amazon supplies claim codes rather than finished cards. The vault stores each claim code as a canonical card record, and at fulfillment it generates a rendered PDF card for every allocated code — Mode B end to end.

Credential shape: Claim code per card Output: Mode B — Generate

Generation happens at fulfillment, not at import — the vault holds only the claim code until an order needs it, then produces the finished PDF cards for that specific fulfillment request.

On-Demand Activation — Walmart

Walmart — the one two-way flow

Walmart is the exception: there is no pre-purchased inventory sitting in the vault. When a paid order arrives, the vault prepares an activation work file, a Progressive team member runs the activation externally with Walmart / Fiserv, and the activated live cards come back into the vault to be allocated and packaged like any other merchant.

Credential shape: Activated live card (on demand) Flow: Two-way — out for activation, back for fulfillment

The round trip is the only difference. Once activated cards are back in the vault, Walmart fulfillment uses the same allocation and output steps as every other merchant — including combining Walmart cards with other merchants' cards in a single customer-ready file.
