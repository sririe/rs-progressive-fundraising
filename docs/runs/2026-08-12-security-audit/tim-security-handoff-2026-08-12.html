1C-06

Walmart import has no reconciliation — bad cards can reach customers

SECURITY P1Gemini ✓highest impact: value loss
Where
src/lib/walmart-preparation.ts, src/lib/inventory-import-service.ts:50, src/app/requests/[requestNumber]/actions.ts:490-651
Mechanism
Imported activated-result rows are validated only for field presence, a permissive success status, and a catalog vendor/type match. They are never reconciled against the order’s own preparation file (expected idempotency keys, denominations, quantities). Rows become globally available and can advance the order to ready_to_allocate.
Impact
A malicious or compromised Operations user — or an honest wrong-file upload — injects attacker-chosen or inactive card numbers/PINs that get allocated to paying customers. Direct value loss / customer harm.
Fix
Persist expected preparation rows/batch identity; transactionally reconcile request identity, idempotency key, denomination, quantity, target system, uniqueness, and an explicit Fiserv success status before a card goes available. Reject extra/missing/cross-request rows; require a review state for partial results.
AcceptAn activated-result file whose rows don’t match this order’s prep batch (wrong keys/denoms/quantities/cross-request) is rejected, not imported. Add a test asserting a mismatched file cannot make cards available.

↳ lane/walmart-import-reconciliation

2C-01

Encryption key enforcement is not fail-closed

SECURITY P1Gemini ✓deploy gate
Where
src/lib/card-secrets.ts:16-41, src/lib/session-token.ts:72-101, render.yaml
Mechanism
Key enforcement is gated on NODE_ENV==='production'. Outside prod a missing key silently uses a hardcoded fallback (and card encryption can fall back to AUTH_SESSION_SECRET). In prod, any non-placeholder string — even one character — is accepted and SHA-256’d into the AES key, with no entropy floor.
Impact
A preview/manual deploy touching real data, or a weak prod key, produces DB ciphertext a reader can decrypt offline. Current Render staging is safe only because its config injects a generated key — the code doesn’t enforce it.
Fix
Require an explicit high-entropy CARD_VAULT_ENCRYPTION_KEY and a separate AUTH_SESSION_SECRET in every non-fixture environment; enforce decoded key length/format; fail at startup, not first use; allow local constants only behind an explicit localhost/test-DB opt-in.
AcceptApp refuses to start (any env that can touch real data) when the encryption key is missing, a known default, or below the length/entropy floor. Add a startup-guard test.

↳ lane/crypto-key-fail-closed

3C-03

Exports aren’t password-protected — the Q7 SOW commitment isn’t built

SOW SPECGemini ✓ · ×3
Where
src/app/requests/[requestNumber]/exports/[exportId]/route.ts:67-116, export builders
Committed
Phase-1 SOW answer to Doug’s Q7:
“The vault generates the password-protected file itself… Each export gets its own randomly generated password, shown once to the operator who created it… the password is never the filename or anything guessable.”
Reality
The app streams plaintext CSV with no password and no ZIP — there is no password-generation path in the code (both finder lanes). This is a build-to-spec gap, not a security-only nicety.
Build
Generate a password-protected package (ZIP-with-password or equivalent) per export; a strong random per-export password shown once to the operator, never filename-derived; log generation. Re-issue = fresh export + new password (already the intended “files are disposable, vault is system of record” model).
Out of scope
Expiring download links / recipient access logs were deliberately deferred to Phase 2 (secure delivery portal) — do not build those now. Unlimited authorized re-download is acceptable under the committed model.
AcceptA generated export is a password-protected file; the password is random, shown once, not derivable from the filename; generation is audited. A trained operator can complete the delivery per the Q7 description without a separate tool.

↳ lane/export-password-protection

4C-04

Work-file download bypasses the download-state machine → double-spend

SECURITY P1Gemini ✓dormant · deploy gate
Where
…/exports/[exportId]/work-file/route.ts:70-124, …/actions.ts:1024-1040, src/lib/feature-flags.ts
Mechanism
The Lloyd work-file route decrypts full credentials and audits, but does not update downloadCount/downloadedAt/allocation state that cancellation-safety relies on. Currently gated off (LLOYD_WORK_FILES_ENABLED=false on staging), so dormant.
Impact
With the flag on: Operations downloads live cards while the order still looks never-downloaded; an Admin cancels → cards return to available inventory → reallocation / double-spend.
Fix
Route all sensitive downloads through one atomic state-transition service (count/time/actor + allocation/request state + audit in one transaction before responding). Cancellation must inspect any sensitive-download event, not one endpoint’s counter. Keep the flag off until fixed.
AcceptAfter a work-file download, the order reflects downloaded state and cannot be cancelled back into available inventory. Test the download → cancel path asserts no card returns to available.

↳ lane/workfile-download-state

5C-P1-1

Account-scoped login lockout → unauthenticated admin-lockout DoS

SECURITY P1Gemini ✓availability · trivial trigger
Where
src/lib/login-attempts.ts:20-28,62-88
Mechanism
Lockout uses an IP-independent account:<login> key that hard-locks after 8 failures / 15 min for 10 min. An unauthenticated attacker POSTing bad passwords for the guessable redstamp username holds the admin locked out indefinitely; IP rotation doesn’t help the defender.
Fix
Keep the account key but degrade to increasing delay / CAPTCHA on the account track (only the per-IP track hard-locks); or add a break-glass admin path; or shorten the account lock and alert on repeated account locks.
AcceptRepeated failed logins against a valid username cannot fully deny that account’s legitimate login from a clean IP.

↳ lane/login-lockout-dos

6C-P1-2

WordPress intake kill-switch is a no-op

SECURITY P1config integrity
Where
WORDPRESS_INTAKE_ENABLED in render.yaml — 0 references in src/
Mechanism
The kill-switch env var is set but never read anywhere. Intake routes are gated only by the HMAC signature. Ops could believe intake is disabled while it stays open to any holder of the HMAC secret.
Fix
Enforce the flag (early 404/503 from both intake routes when it isn’t "true"), or remove the var so config doesn’t imply a control that doesn’t exist.
AcceptWith the flag off, a validly signed intake POST is rejected.

↳ lane/wordpress-intake-killswitch

7C-02

Password hashing below current OWASP scrypt minimum

SECURITY P1
Where
src/lib/password.ts:1-19
Mechanism
scryptSync uses Node defaults (N=2¹⁴) and stores no cost/version — materially below OWASP’s current scrypt guidance. Salt + timing-safe compare are correct.
Fix
Argon2id (or calibrated scrypt at a current minimum); encode algorithm + all cost params per hash; rehash on successful login when params are stale.

↳ lane/password-hash-argon2id

8C-05

Quadratic CSV parse → import DoS

SECURITY P1confirmed by local timing
Where
src/lib/inventory-import.ts:335-447
Mechanism
Per row the parser rescans the whole accumulated issues array (issues.some(...)) → O(rows × issues). Measured: 8,000 bad rows = 1.35 s vs 27 ms at 1,000; a sub-1 MB payload can hold >100k tiny rows and tie up the event loop. Repeatable by a compromised Operations account.
Fix
Row-local error flag/count; cap rows / issues / field-length / total bytes; stop after a bounded error threshold; prefer a streaming parser; add adversarial perf tests.

↳ lane/csv-parse-dos

9C-07

CSV-injection neutralization misses full-width formula initiators

SECURITY P1Gemini narrowed
Where
src/lib/export-csv.ts:1-24 (+ import predicate)
Mechanism
Sanitizer apostrophe-prefixes ASCII = + - @ including leading whitespace. Verifier correction: TAB/CR/LF are handled (consumed as leading whitespace) — the real, confirmed gap is full-width variants (e.g. ＝), which pass through unescaped on both import and export. Spreadsheet/locale-dependent.
Fix
Neutralize the full target-spreadsheet prefix set including full-width variants at every untrusted input/output boundary; add LibreOffice/Excel behavioral tests.

↳ lane/csv-injection-fullwidth

The two 500s — engineering dispositions

Walmart upload-500 (777059612) — the fixture parses cleanly locally; the upload branch diverges at getUploadedTextFile (File.text()), 1 MB check applied post-decode. Most likely upload transport/runtime/deploy handling, not a malicious parse path; it did not corrupt state. Confirm against Render logs.

Create-order 500 (294045514) — most likely a request-number race (read-then-create on the unique order number in fulfillment-request-service.ts). No raw SQL, no card data in the error path. (Both also filed in the design-QA handoff as P0-1 / P0-2.)

Verified good — controls that hold

  • ✓AES-256-GCM authenticated encryption, fresh random 12-byte IV per field; unknown-version ciphertext fails unreadable.
  • ✓Card secrets decrypt in exactly two role-gated (Admin/Operations) + audited download routes. Finance/Viewer get 403. No “reveal full card in UI” path.
  • ✓Q5 / Q6 SOW answers already hold: masked values everywhere on screen; the export download log is the complete sensitive-access record; append-only audit log (no update/delete in code).
  • ✓Production CSP is real (nonce-based, via src/proxy.ts middleware — not next.config.ts); session secret fails closed in prod.
  • ✓No raw SQL ($queryRaw/$executeRaw absent), no dangerouslySetInnerHTML, no server-side SSRF fetch of the Fiserv URL; export IDs bound to their request; download filenames sanitized (no path traversal).

P2 — defense-in-depth (post-P1)

Post-login open redirect via /\ slash-backslash normalization · WordPress HMAC replay window (±5 min, no nonce store; bounded by downstream idempotency) · PHP mu-plugin keeps HMAC secret in wp_options plaintext by default (order-injection only, no card read) · spoofable client-IP headers fragment the per-IP throttle · non-constant-time bearer-secret compare (gated off on staging) · env-secret intake path skips isSiteAllowed · single SHA-256 key reused for GCM + HMAC (no HKDF domain separation / rotation) · one corrupted ciphertext can 500 a whole export (no per-record quarantine) · Fiserv URL accepts any HTTPS host incl. loopback (Admin-planted client-side link).
