## 4. Answers to Doug's security questions

### Q5 — Who can decrypt/view full card numbers and PINs?

At the application layer, **Admin and Operations** users can retrieve full values through the normal export route (`exports/[exportId]/route.ts:28-31,78-99`) and, when enabled, the Lloyd work-file route (`work-file/route.ts:32-35,80-95`). Finance and Viewer are rejected. The permissions table states the same role intent at `src/lib/permissions.ts:63-67`.

The only production card-decryption imports are those two routes; the UI elsewhere reads masked columns. `decryptCardSecret` is also used for stored **WordPress connection secrets**, not cards, in `src/lib/integrations/wordpress-connections.ts:115-124` and is gated to Admin actions.

Outside the application role model, anyone who can obtain both the database ciphertext and `CARD_VAULT_ENCRYPTION_KEY` can decrypt offline using the repository code. That includes the running application process and any infrastructure/operator account with both Render environment-secret access and DB access. A DB-only reader does not get the key from the schema; a key-only holder does not get the ciphertext. The reviewed staging key is Render-generated (`render.yaml:23-26`).

### Q6 — Is viewing sensitive card data audited?

Within this lane's full-card view surface, **yes, but tracking semantics differ**:

- Normal export download updates count/time/actor and writes `sensitive_data.export_downloaded` in one transaction before returning the CSV (`route.ts:117-167`).
- Work-file download writes `sensitive_data.work_file_downloaded` before returning (`work-file/route.ts:107-124`), but does not update the canonical export/request/allocation download state (C-04).
- No browser page directly renders decrypted card values; card pages use masked fields. Audit-log integrity/tamper resistance is owned by the sibling lane.

### Q7 — Export file security

- **Format/password:** normal output is plaintext CSV, not ZIP. There is no ZIP library or password-generation path, so password strength/ownership is **none / nobody**. The old analyzed script derived a password from filename digits, but that script is not this app's implementation.
- **Server storage/deletion:** no generated customer file is persisted; the CSV is built in memory per GET. Therefore there is no server file to delete. However, the export record and regenerable endpoint have no expiry/revocation/deletion state (C-03), and downloaded local files are explicitly Progressive's responsibility (`docs/production-readiness-checklists.md:15-17`).
- **Authorization / IDOR:** both export routes require an active Admin/Operations session and bind `exportId` to the supplied `requestNumber` in one Prisma `findFirst` (`route.ts:28-64`; `work-file/route.ts:32-68`). I found no unauthenticated or mismatched-ID download. Roles are global rather than client-scoped; that is the intended current matrix, not an export-route bypass.
- **Tracking:** normal downloads are atomically counted/audited and set allocation/request state. Work-file downloads are audited only and bypass the state fields (C-04).
- **Caching/headers:** both routes return `Cache-Control: private, no-store`, attachment disposition through a CR/LF/path-character sanitizer, `text/csv`, and `nosniff` (`route.ts:169-176`; `work-file/route.ts:117-124`; `src/lib/http-security.ts:36-46`).
- **CSV injection:** every production CSV builder found uses `buildCsv`; `= + - @` including whitespace-before-formula are neutralized on output and rejected on inventory import. Coverage is incomplete for direct control-character/full-width prefixes (C-07).
- **Path traversal:** the work-file route performs no filesystem access. Route params only constrain a Prisma query; the response filename is generated from a stored request number and sanitized. No traversal sink exists.

## 6. The two observed 500s

- **Walmart file-upload 500 (`ERROR 777059612`):** the exact uploaded bytes parse cleanly locally, and the same file reportedly succeeds when pasted. The upload-only branch diverges before parsing at `getUploadedTextFile` (`src/app/requests/[requestNumber]/actions.ts:90-105,490-517`): it receives a multipart `File` and calls `File.text()`. The code checks the file's 1 MB limit only after decoding it, although Next's documented Server Action body limit is also 1 MB. Static/local evidence does **not** establish why this 10.5 KB file fails on Render. Best bounded conclusion: likely upload transport/runtime handling or deployment-specific error, not a malicious parse/validation path. It did not corrupt state in QA, and the parser's independent DoS issue is C-05.
- **Create-order 500 (`ERROR 294045514`):** separate path. Manual create uses Prisma APIs, no raw SQL, and its unhandled validation/business errors contain no card secrets (`src/app/requests/new/actions.ts:78-156`; `src/lib/fulfillment-request-service.ts:121-175`). Request numbers are calculated with a read-then-create sequence (`fulfillment-request-service.ts:58-75,175-193`), so concurrent creates can race the unique request number; this is a plausible availability explanation, not proven without logs. The client error digest is opaque and no source logging of submitted PII/card data was found. No injection finding is claimed from this 500.

## 7. P2 / P3 hardening and verified-negative notes

- **P2:** `card-secrets.ts:38-41,115-120` reuses one SHA-256-derived key for AES-GCM and HMAC fingerprints and has no key ID/rotation path. Derive domain-separated subkeys with HKDF and add explicit key-version rotation/re-encryption support.
- **P2:** decryption format/auth failures throw at `card-secrets.ts:102-112`; one corrupted allocated ciphertext can 500 the whole export. Catch per-record failures, fail the export safely with a security/audit event, and provide an operator-visible quarantine path without exposing plaintext.
- **P2:** file `accept` is client-only (`walmart-result-import-form.tsx:191-199`); server checks decoded size but not MIME/extension, field length, row count, or binary content. Content parsing is the primary defense, but bounded server validation would reduce ambiguity and resource abuse.
- **P2:** Fiserv is **not SSRF**: no server-side `fetch`/HTTP client consumes it; it is an Admin-written link rendered to the operator (`integrations/wordpress/actions.ts:37-60,213-249`; `walmart-result-import-form.tsx:127-135`). It accepts any HTTPS host, including private/loopback destinations, so allowlist approved Fiserv origins to prevent an Admin account from planting a client-side internal-network/phishing link.
- **P2:** replace the hand-rolled line parser (`inventory-import.ts:53-84`) with a bounded RFC-aware parser. It does not reject unbalanced quotes or support quoted newlines; current action-level blocking prevents observed partial corruption, but format ambiguity is unnecessary around cash-equivalent data.
- **P3 / verified good:** AES-256-GCM is authenticated; each field receives a fresh random 12-byte IV (`card-secrets.ts:71-86`); unknown versions fail unreadable; production placeholder values are rejected; 16-byte password salts and equal-length `timingSafeEqual` are used.
- **P3 / verified good:** no `$queryRaw`, `$executeRaw`, unsafe variants, shell/eval, `dangerouslySetInnerHTML`, or card-data server fetch sink was found. Prisma object queries are parameterized and React renders stored card/customer values as text.
- **P3 / verified good:** attachment filenames strip CR/LF, quotes, slash, and backslash (`http-security.ts:36-46`); export IDs and request numbers are query values, never paths.
